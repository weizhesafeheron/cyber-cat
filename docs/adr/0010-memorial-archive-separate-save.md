# 0010 - 猫的档案是独立存档，告别页是它的只读视图

日期：2026-07-29
状态：已采纳

## 背景

猫死了之后要做三件事（[mvp-scope 第 7 节](../mvp-scope.md)、CONTEXT.md 的「猫的档案」）：

1. 以安静的告别页呈现，含陪伴天数、喂食次数、抚摸次数，可翻看它一生的日记；
2. 旧猫进入猫的档案，档案保留历任猫；
3. 可无惩罚地领养新猫。

第 3 条与第 2 条直接冲突。领养新猫要走 `createWorld`，产出的 world 会覆盖 `world.json` -
而旧猫的一生（`stats`、`diary`、`diedAt`、`identity.bornAt`）全部只存在那份文件里。
按当前的日记上限（`DIARY_MAX_ENTRIES = 400`）这是几百条不可再生的数据：那只猫已经死了，
没有任何办法把它的一生重新演化出来。

同时，世界层是纯函数、不读时钟、不持有屏幕坐标（[ADR 0001](0001-offline-catchup-simulation.md)），
而告别页要显示的是「2026-06-01 - 2026-07-05，陪伴 34 天」这类东西 - 日期与时区属于呈现。

## 决策

**猫的档案是第三份存档 `memorial.json`，有自己的版本号；告别页是它的只读视图，
自己读文件，不向宠物窗口要数据。**

四个具体后果：

### 1. 档案不进 `world.json`

`world.json` 是「当前这只猫」，领养新猫时整份被覆盖。
档案的生命周期比任何一只猫都长，塞进去等于每换一只猫就把历任猫抹掉一次。

这与挂件摆放另存一份（`props.json`，见 [props/save.ts](../../src/props/save.ts) 的注释）是同一条理由的另一个方向：
那边是「屏幕坐标不能进平台无关的世界层」，这边是「比世界更长寿的数据不能放在会被覆盖的文件里」。

版本号也是独立的（`MEMORIAL_SAVE_VERSION`）。共用 `WORLD_VERSION` 会让「改了世界结构」
连带要求丢掉整份档案 - 而世界存档丢了只是重新领养一只猫，档案丢了不可挽回。

### 2. 档案只存无法重建的东西

一条记录 = 身份四元组 + `diedAt` + `stats` + 死亡时的日记快照。

**不存**外观、性格（由「品种 + Seed」完整重建，[ADR 0002](0002-procedural-pixel-cats.md)）、
陪伴天数（由 `bornAt` 与 `diedAt` 算出）。存了就有两份真相，而这份文件会在磁盘上躺很久，
两份真相有足够的时间漂移。

### 3. 入档由宠物窗口做，且必须幂等

入档发生在宠物窗口**发现**猫死了的时候，不是「猫死了的那一刻」 - 三种情况走同一条路：
实时跑到死、离线补算跨过死亡链、上次运行时就死了而用户直接关掉了告别页。
所以去重是必需的（按 `seed + bornAt`），不是保险：不去重的话每次启动都会往档案里加一条同一只猫。

一条刻意的不对称：**档案读坏了绝不覆盖。**
`world.json` 与 `props.json` 读坏了都退回默认（重新领养、挂件回到默认位置），
而档案读坏了只报错、不写盘、保留那份坏文件 - 覆盖掉就等于把用户养过的所有猫一起删了。
所以 `loadMemorial` 是三份存档里唯一**读坏了会抛**的那个。

### 4. 告别页自己读文件，不跟宠物窗口要数据

告别页是第四个 webview。可选的做法有两条：

- 宠物窗口把死掉那只猫的数据 emit 过去；
- 告别页自己 invoke `load_memorial`。

选后者，三个原因：

- **告别页本来就要读整份档案**（「档案保留历任猫」，点一条能翻回那只猫的日记）。
  走事件的话仍然要再读一次文件，等于两条数据来路。
- 事件有先后顺序的坑：接收方必须在发送方 emit 之前挂好监听，领养流程为此专门有一条
  「先挂监听再开窗」的纪律（[app/adoption.ts](../../src/app/adoption.ts) 的 `requestAdoption`）。
  只读文件没有这个问题。
- 宠物窗口在死亡那一步就会立刻存盘（`world/tick.ts` 发出 `died` 事件 → main.ts 的
  「有事发生就立刻存」），而入档排在开窗之前，所以告别页打开时文件已经是全的。

代价是告别页多一次读文件（几毫秒），换来它是一个**纯只读视图** -
世界状态仍然只有宠物窗口持有，与挂件窗口同一条不变量。
用户点「再养一只」时它只 emit 一个空事件，领养仍然走宠物窗口里那一个 `step`。

## 被否决的方案

**把 `stats` 与 `diary` 留在 world.json 里，领养新猫时把旧的 world.json 改名备份。**
文件名要带时间戳，于是「档案里有几只猫」变成了「目录里有几个文件」，
列出历任猫要先扫目录再逐份解析，而每一份都是完整的 World（含随机源状态、行为节拍计数
这些对一只死猫毫无意义的字段）。放弃。

**让 World 多一个 `memorial: MemorialEntry[]` 字段，领养新猫时把它搬到新 world 里。**
搬运这一步是唯一一处必须记得做的事，忘了就静默丢掉全部历史 -
而它只在「第二只猫死掉之后」才看得出来。这类必须记得的约定迟早会忘。放弃。

**死亡也发一条系统通知。** 告别页本身是一个居中弹出的窗口，比通知重得多，
再加一条通知只是把同一件事说两遍。系统通知只在**生病**这一级发（issue #13），
理由见 [app/notify.ts](../../src/app/notify.ts)。

## 影响

- 新增 `memorial.json`（Rust 侧 `save_memorial` / `load_memorial`）。
- 新增按需窗口 `farewell`，与领养窗口同构但**关掉不退出应用**（猫死了，退出等于把
  「再养一只」这条路也关掉），并因此给 `open_adoption` 加了 `exit_on_cancel`：
  首次启动放弃领养该退出，告别页之后放弃领养不该退出。
- 托盘多一项「告别与档案」，仅猫离开后可用。它不是可选的：告别页能被关掉，
  而它同时是领养新猫的唯一入口。
- `WORLD_VERSION` **不动**：World 的结构没有任何变化。
