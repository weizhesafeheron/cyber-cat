# 0012 - 表面模型：猫可以停在窗口上沿，但纵向永远不是自由变量

日期：2026-07-30
状态：已采纳

## 背景

「猫爬到前台窗口上」（MVP 特效 3.1，issue #12）是桌面宠物形态的核心价值体现，也是第一次**猫可以停在别的高度上**。

在此之前空间模型只有一条线：猫、食盆、猫窝都踩在同一条地面线上（`groundScreenY`），猫只有 x 没有 y。
唯一的例外是 ticket 10 的 `MotionState.liftY`（猫离地面线的高度），而它只在被拎着与下落时非零 - 产品口径是「猫可以离开地面，但**不会停在**那里」，松手必然落回 0。

爬窗口打破的正是那个「不会停在那里」。
问题是怎么打破：给猫一个自由的 y，还是别的什么。

## 决策

### 一、猫站在**表面**上，`liftY` 由表面推出来

引入表面（`PerchSurface`）：一条可以站的横线，带屏幕 y 与横向可站区间。

- 桌面的地面线是其中一个表面（隐式的那个，永远存在）；
- 前台窗口的可见上沿是另一个；
- 猫任何时刻站在某一个表面上，`liftY = 地面线 y - 当前表面 y`。

于是纵向仍然不是自由变量，而「猫可以离开地面但不会停在半空」这句口径有了精确形式：
**被拎着与下落时没有表面，所以必然落回地面；站在窗口上时有表面，所以停得住。**

由此直接推出而不需要另写规则的两条：

- **食盆与猫窝在桌面那条线上，所以猫要吃饭或睡觉必须先跳下来。** 判断层看到世界层给了挂件锚点就撤销表面，运动层于是先落地，落地之后才走向挂件。
- **爪印落在猫脚下那条表面上**，不是桌面地面线（否则猫在窗口上走，脚印出现在几百像素下方的桌面上）。

### 二、表面是**每帧续约**的，撤销邀请就是下来

运动层每帧收一个 `perch: PerchSurface | null`，语义是「这一帧允许你待在这条边上」：

| 输入变化 | 猫的行为 |
|---|---|
| null → 一条表面 | 走到起跳点，跳上去 |
| 同一条（`id` 相同），几何可变 | 待着，跟着窗口上下左右走 |
| → null，或换了 `id` | 跳下来 |

刻意**不做「上去/下来」两个命令**。理由是失效方向：任何一处出问题（轮询停了、窗口读不到、世界层改主意、上层忘了调用），猫都回到桌面那条永远存在的表面上；而漏掉一次「下来」会把猫永久留在半空。

### 三、三层分工，与挂件锚点（[ADR 0009](0009-prop-anchors-across-layers.md)）完全对称

| 层 | 负责 | 不知道 |
|---|---|---|
| 平台层 `platform.rs` | 前台窗口是哪个、可见矩形、所在屏的 DPI | 猫想干什么 |
| 判断层 `app/perch.ts` | 那条边能不能站、这一刻要不要上去、待多久 | 怎么跳、跳多久 |
| 运动层 `app/motion.ts` | 逐帧把猫送上去、在上面走、跳下来 | 表面是窗口还是别的什么 |

**世界层只出两个投影**（`status` 与 `anchor`），它连屏幕上有没有窗口都不知道。
屏幕矩形一旦进 World，同一份存档在不同分辨率的机器上就会演化出不同的猫，离线推演的可回放性当场失效（[ADR 0001](0001-offline-catchup-simulation.md)）。

### 四、三个新动作，纵向位移仍然归运动层

`leapUp`（跳上高处）、`leapDown`（从高处跳下）、`edge`（在窄边缘行走），全部列入 `MOTION_ONLY_ACTIONS` - 世界层不知道有窗口可爬，因此永远不会选它们。

跳跃的**纵向位移不在动作里**：猫贴着舞台下沿（[ADR 0007](0007-stage-window-and-motion-layer.md)），升高靠整块舞台窗口上移。
这与走路用 `travel`、扑跳用 `leap` 把位移交给运动层是同一个契约 - **动作库只负责形体。**

腾空时长按 `v0 = sqrt(2 g lift)` 算（重力与下落共用一个常数），所以跳得高就飞得久。
被否决的做法是固定 0.4 秒配 easing：真实桌面上窗口高度任意，那样跳一个台阶与跳一层楼的速度感完全一样。

## 理由与被否决的方案

**为什么不给猫一个自由的 y。**
「脚踩实地是硬约束」是既定结论（art-and-motion-decisions）：所有姿态的脚底线都画在同一条精灵行上，任何整帧纵向平移都会把脚一起抬起来，实测一眼被看破。
自由的 y 意味着猫可以停在任意高度，而那个高度下面**什么都没有** - 它必须由某个东西支撑，那个东西就是表面。
另一半代价是传染性：爪印、挂件、爱心、气泡都要跟着从「一条线」变成「二维」，而它们里只有爪印真的需要。

**为什么不在世界层加一个 `perch` 字段。**
最像 ADR 0009 的做法（那边世界层出 `anchor`），但这里不成立：
「能不能待在高处」完全可以由已有的两个投影（`status`、`anchor`）推出来，加字段就有两份真相；
而「这一帧要不要起跳」需要帧时钟与随机源（站稳判定、冷却、按活跃度抽签），世界层两样都没有 - 30 分钟一步的整步上没有「这一帧」。
所以世界层不动一行，判断层读它的投影。

抽签有一个产品手感上限：同一窗口站稳后仍未抽中，约 15 秒就发出邀请。活跃度仍决定猫是否更早想到要上去，但不允许坏运气让功能几分钟没有反馈。坐下与趴下是可自然离开的循环姿势，邀请会让运动层先改播走路、再到起跳点；舔毛、吃饭、睡觉与一次性动作仍不会被打断。20 秒冷却只用于防止猫刚下来又立刻上去，应用启动时不额外等待它。

**为什么不让运动层直接读窗口矩形。**
与 ADR 0009 拒绝「运动层直接读挂件状态」同一条理由：那样运动层会跟着窗口 API 一起变（多显示器、cloaked、DPI），而且它拿到矩形之后就有了做决定的材料，「谁决定猫做什么」这条线会开始模糊。
现在它只收四个数：`id` / `y` / `min` / `max`。

**为什么跨 DPI 时不上去而不是缩放贴图。**
猫的贴图缩放由**舞台窗口所在屏**决定（display.ts 的「每个源像素占整数个物理像素」规则），目标窗口在另一个缩放的屏上时两者必然不同。
MVP 不做多显示器穿越（mvp-scope 第 10 节），所以直接不上去；要支持的话得先解决「猫跨屏时贴图缩放跳变」这件独立的事。

## 已知取舍：最大化窗口的上沿爬不上去

这是与 issue #12 验收项「最大化/还原都能正确落在可见顶边上」的一处**明确冲突**，写在这里而不是偷偷放宽闸门。

算术是这样的：猫贴着舞台下沿（ADR 0007），脚底线离舞台下沿只有 6 个精灵像素，所以要让脚落在屏幕 y 上，舞台顶端必须在它上方 222 CSS 像素（三倍缩放）处。
最大化窗口的上沿就在工作区顶端，于是舞台整个跑到工作区之外 - 露在外面那一段里的猫会被系统裁掉。
换句话说：**一只 129 像素高的猫，站不到距屏幕顶端不足 129 像素的边上**，这跟代码怎么写没关系。

因此 `maxPerchLift(geom) = 工作区高 - 舞台高`，超过就不给表面（失效方向是「猫留在桌面上」）。
1080p、菜单栏 25 像素的屏上，可爬的窗口上沿要低于 y ≈ 247。

三条备选都不可行或不可接受：

1. **让舞台升出工作区。** 猫会被屏幕顶端裁掉；macOS 上还会被菜单栏盖住（菜单栏的窗口层级高于我们的浮动层）。
2. **把猫在舞台里的纵向位置改成可变。** 舞台高 240、猫高 168，最多腾出 54 像素，离 222 差得远；而且改这一条要动 ADR 0007 的「猫贴着舞台下沿」，命中测试与三个覆盖层的定位全都挂在上面。
3. **让猫站在标题栏下沿而不是上沿。** 身体照样向上伸出屏幕，只是少了标题栏那 28 像素，治不了根。

真要支持最大化窗口，得换成一个可以覆盖整条屏幕上边缘的窗口（全屏透明窗口在 ADR 0007 里已被否决）或者接受猫被裁掉一半。
**这是产品判断，不是实现细节**，留给产品负责人决定。

## 影响

- `MotionState` 多一个 `perch` 字段（不进存档，与运动层其余状态同理）。
- 舞台里所有按脚底线定位的覆盖层都要改成用 `footScreenY(geom, liftY)`，不能再直接用地面线。爱心已经改了；回归气泡与台词气泡按精灵坐标定位，天然跟着猫走，不受影响。
- 轮询：默认 10 Hz，猫静止时 2 Hz，睡眠与锁屏时停止。后者是**结构保证**而不是定时判断 - 轮询由帧循环驱动，而 rAF 对隐藏/被遮挡的窗口不触发。
- **安静模式待接**（mvp-scope 第 6 节「不爬前台窗口」）：它还没实现，实现后与 `perchAllowed` 求与即可。
- Windows 侧的平台代码按调研文档写成，并在 `x86_64-pc-windows-msvc` 目标上类型检查通过，但**未在真机运行验证**。
- 后续若要让猫在多个窗口之间跳，必须引入 `EnumWindows` 并加 `DWMWA_CLOAKED != 0` 过滤（ADR 0005 的实机结论）。
